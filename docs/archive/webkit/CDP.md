# Chrome DevTools Protocol

zebkit is meant to be embedded in agent applications, and the tools agents
drive a browser with (Puppeteer, Playwright, and libraries that speak the
protocol directly) all talk the Chrome DevTools Protocol. WebKit does not.
It has its own Web Inspector Protocol, which reports much of the same
information in different shapes and has nothing for the browser-level parts:
opening pages, navigating, mouse and keyboard.

The engine therefore carries a CDP endpoint of its own (`src/cdp`, compiled
into `libzebkit`). It serves the HTTP and WebSocket interface CDP clients
expect, answers what it can from the WebKit API, and translates the rest to
and from the Web Inspector Protocol.

**This is a subset of CDP, not Chrome.** It covers what automation needs and
is tested with real clients; the tables below say exactly what is in and
what is not. A method that is not implemented answers with CDP's "wasn't
found" error instead of pretending to succeed.

## Using it

Start the endpoint in one of two ways:

- Set `ZEBKIT_CDP_PORT` in the environment of any application that embeds
  the engine. `ZEBKIT_CDP_ADDRESS` chooses the address (default
  `127.0.0.1`); port `0` lets the system pick.
- Call `zebkit_cdp_listen(address, port, &error)` from the
  application. The header is `src/cdp/zebkit-cdp.h`; `scripts/package.sh`
  puts a copy in the package's `include/`. `zebkit_cdp_stop()`
  disconnects every client, closes the pages the endpoint opened and stops
  listening.

On start the engine prints the line Chrome prints,
`DevTools listening on ws://127.0.0.1:PORT/devtools/browser/ID`, and every
`WebKitWebView` of the process becomes a page a client can attach to.

```js
// Puppeteer
const browser = await puppeteer.connect({ browserURL: 'http://127.0.0.1:9222' });
// Playwright
const browser = await chromium.connectOverCDP('http://127.0.0.1:9222');
```

`tools/cdphost` is a complete embedding application in 90 lines: one view
and a call to `zebkit_cdp_listen()`.

### Pages the client opens

`Target.createTarget`, `/json/new` and `window.open()` need a new view. By
default the endpoint creates one itself, with the settings, web context and
display of the application's first view, and destroys it when it is closed.
A window a page opens becomes such a view only while a client is connected;
with nobody to see or close it, it would stay for the life of the process.
An application that wants to own these views (to put them in its own
windows, say) registers a function with
`zebkit_cdp_set_create_view_func()`.

`Target.createBrowserContext` gives a context with its own cookies, cache
and storage, backed by an ephemeral `WebKitNetworkSession`.

### Who can connect

The endpoint gives full control of the browser to whoever reaches it, as
Chrome's does. The same precautions apply and the same defaults are built
in:

- It listens on `127.0.0.1` unless told otherwise. Do not bind it to a
  public address; put an authenticated tunnel in front if it must be
  reached from another machine.
- HTTP requests are refused unless their `Host` header is an IP address or
  `localhost`, so a web page cannot reach the endpoint through a host name
  it controls.
- WebSocket connections and HTTP requests that carry an `Origin` header
  (that is, come from a web page) are refused. `ZEBKIT_CDP_ALLOW_ORIGINS`
  takes a comma-separated list of origins to allow, or `*`.
- `/json/new` needs the `PUT` method, as in Chrome since version 111: a
  page can send a `GET` anywhere without asking.

**There is no password.** With the defaults, any program running on the
same machine, under any user, can ask `/json/version` where the sockets are
and take over the browser, which includes reading its cookies and, through
file inputs and `file:` addresses, the files the application can read. That
is how Chrome's port behaves too, and it is fine on a machine that only the
agent's owner uses. Where it is not:

- Call `zebkit_cdp_set_discovery_enabled(FALSE)` before listening,
  or set `ZEBKIT_CDP_DISCOVERY=0`. The `/json` pages are then not served,
  and the browser socket is reachable only at the address
  `zebkit_cdp_get_url()` returns (the same one the engine prints on
  its standard error), which contains a random 122-bit id. Hand that
  address to the client: `puppeteer.connect({ browserWSEndpoint })`,
  `chromium.connectOverCDP(wsEndpoint)`.
- A message larger than 256 MiB closes the connection.

## The standard it is held to

The endpoint is written against Chrome's own material, not against a
reading of the documentation:

- **The protocol definition is Chrome's.** `deps/devtools-protocol`
  holds the two files Chrome generates its protocol code from, unchanged,
  at a pinned revision. The endpoint checks the parameters of every command
  it implements against them before the command reaches its handler
  (`src/cdp/CDPProtocol.inc`, generated by `scripts/gen-cdp-protocol.py`),
  and answers a mismatch as Chrome does: `-32602 Invalid parameters` with
  the name of the parameter. The tests check every result and every event
  the endpoint sends against the same files.
- **Chrome is the reference for behaviour.** `scripts/cdp-reference.sh` runs
  the raw protocol checks against a real Chrome. A check Chrome fails is a
  wrong check. The first such run failed 15 of 34 checks, and going through
  them found about forty places where zebkit answered differently from
  Chrome; "Held to Chrome's definition and Chrome's behaviour" below
  lists them. The handful of things zebkit does
  on purpose and Chrome does not are marked in the tests and listed under
  "Differences from Chrome" below.
- **Chrome's implementation itself cannot be used.** It is not a library:
  the code behind each command is part of Blink and V8 and calls their
  internals (`InspectorDOMAgent` walks Blink's DOM, `V8RuntimeAgentImpl`
  holds V8 handles). There is nothing in it that could be compiled against
  WebKit. What can be shared is the definition, which is vendored, and the
  behaviour, which is tested.
- **Where WebKit lacks something, WebKit is patched**, the way Playwright
  does for the WebKit it ships. So far that is one patch
  (`patches/2006-inspector-user-worlds.patch`): isolated worlds, and
  resolving a node in a chosen world.

## How it works

```
CDP client ── WebSocket ──> src/cdp (UI process)
                              ├─ WebKit API: navigation, input, views, cookies, dialogs
                              └─ Web Inspector Protocol ──> page (web process)
```

| File | What is in it |
|---|---|
| `CDPPlatform.h` | The line between portable code and what a platform supplies. The files named `GLib` are the Linux layer, those named `Cocoa` the macOS one, those named `Win` and `CDPViewProxy.cpp` the Windows one (`docs/WINDOWS.md`); the rest is portable |
| `CDPServer.cpp` | HTTP discovery, sockets, sessions, and the `Target`, `Browser` and `Storage` domains |
| `CDPPage.cpp` | One page: the inspector connection, and the page's events translated to CDP |
| `CDPDomains.cpp` | `Page`, `Runtime`, `DOM`, `Network`, `Emulation` commands |
| `CDPView.cpp` | What goes through the view, as far as it is the same everywhere: the bookkeeping of a navigation, dialogs, the order of input answers |
| `CDPViewGLib.cpp`, `CDPViewCocoa.mm` | The view itself: navigation, mouse and keyboard, window size, dialogs, file choosers, cookies, creating views |
| `CDPTransportGLib.cpp`, `CDPTransportCocoa.mm` | The listening socket and the C API. On Linux, HTTP and WebSockets are libsoup's |
| `CDPWebSocket.cpp` | HTTP requests and WebSockets over a plain connection, for macOS, where no system library serves both on one port |
| `CDPImage.cpp`, `CDPImageCocoa.mm` | JPEG and WebP screenshots (Skia); on macOS JPEG only (ImageIO) |
| `CDPProtocol.inc` | Generated: the implemented commands and their parameters, from the standard definition |

Things worth knowing when something behaves unexpectedly:

- **Input is real input.** Mouse and key events are delivered to the view
  as platform events, the path a physical mouse and keyboard take. Pages see
  trusted events, and focus, text entry and link activation happen as they
  would for a user. A command is answered after the page has handled the
  event.
- **Navigating to another site can move the page to a new process.** WebKit
  then creates a second inspector target and commits it later. The endpoint
  sets up each new target (enabled domains, scripts for new documents,
  bindings, extra headers, user agent) before it is allowed to load, and
  keeps the page's frame id the same throughout, so clients do not notice.
- **Isolated worlds are WebKit user worlds.** A world a client asks for
  (`Page.createIsolatedWorld`, or a `worldName` on a script or a binding)
  has its own global object in each frame: the page cannot see what a
  client puts there and the client's scripts do not see the page's
  variables. Both see the same document. A node goes from one world to
  another the way it does in Chrome, `DOM.describeNode` and then
  `DOM.resolveNode` with an `executionContextId`. WebKit's inspector
  protocol had neither; `patches/2006` adds them. WebKit makes each world in
  every frame; as in Chrome, a client is told of a world's context only in
  a frame where it created the world, or everywhere if it registered a
  script for the world. At most 16 worlds per page.
- **Parameters are checked before a command runs**, against the standard
  definition: a mandatory parameter left out or one of the wrong type is
  refused with `-32602`, as in Chrome. Parameters the definition does not
  know are ignored, as in Chrome.
- **A document that changes its own address** (a fragment, the history API)
  is reported with `Page.navigatedWithinDocument` for the main frame.
  WebKit's protocol has no such event; the endpoint notices the view's
  address change and asks the document whether it is still the same one.
  Child frames are not covered.
- **A client that starts listening late is told where the page is.**
  `Page.setLifecycleEventsEnabled` replays `commit`, `DOMContentLoaded`,
  `load` and the network-idle events for what has already happened, as
  Chrome does.
- **Frames are part of their page.** There are no separate targets for
  iframes or workers, also for frames of another site; they are reached
  through the page's session, with their own execution contexts.
- **Ids are the bridge's.** The main frame has the target's id, as in
  Chrome. WebKit numbers other frames, loaders and requests per process,
  starting over in each one, so those ids get a prefix that changes when
  the page changes process.
- **The back/forward cache is off while a client is attached.** WebKit's
  inspector does not report the script contexts of a page restored from it,
  so history navigations load the page again. The setting is the
  application's `WebKitSettings`, which views may share; it gets its own
  value back when the last attached page is released.
- **What a client changes outside the page is undone when it leaves:** the
  view's size (`Emulation.setDeviceMetricsOverride`), ignored certificate
  errors, and a dialog it was shown and did not answer, which would
  otherwise hold the page's script for ever.
- **When the page's process dies** clients get `Inspector.targetCrashed`,
  commands that were waiting and commands sent afterwards fail with
  "Target crashed", and `Page.navigate` or `Page.reload` brings the page
  back in a new process with the client's setup applied again.
  `Page.crash` kills the process on purpose.
- **Answers to input commands keep the order of the commands.** Clients
  send a press and its release together and work out which buttons are down
  from the order of the answers.
- **A failed navigation** is reported (`errorText` from `Page.navigate`)
  after WebKit's error page has committed, so that the commit is not taken
  for part of the next navigation.
- **"Network idle" is computed**, as Chrome defines it: after the load
  event, `networkAlmostIdle` when at most two requests have been in flight
  for 500 ms and `networkIdle` when none has.
- **`/devtools/wip/<targetId>`** is a WebSocket that carries WebKit's own
  protocol untranslated, for clients that speak it and for debugging the
  bridge. Do not use it on a page that also has CDP sessions.

## What is not covered

| Missing | What it means for a client |
|---|---|
| `Fetch` domain, `Network.setRequestInterception` | No request interception or mocking: `page.setRequestInterception()`, `page.route()` fail. WebKit's protocol has interception, so this can be added. |
| `Accessibility.getFullAXTree`, `DOMSnapshot` | Clients that read the page through the accessibility tree or DOM snapshots need another way (script in the page, `DOM.getDocument`). Playwright's `getByRole` works: it is computed by script. |
| `Input.dispatchTouchEvent`, drag-and-drop interception | Mouse and keyboard only. |
| `Emulation`: device scale factor, mobile mode, touch, geolocation, timezone, locale, CPU and network throttling | `setDeviceMetricsOverride` changes the size only. |
| `Page.printToPDF`, screencast, `Tracing`, `Performance.getMetrics`, `Profiler`, `HeapProfiler`, `Debugger`, `CSS` | No PDF output, tracing, profiling or script debugging over CDP. |
| Downloads | `setDownloadBehavior` is acknowledged; downloads follow the application's WebKit download handling, and no download events are sent. |
| Workers and service workers as targets | Not visible to the client. They run. |
| Permissions (`Browser.grantPermissions`) | Acknowledged, not applied; permission requests go to the application. |
| `fromSurface`, `scale` in clips | Screenshots are software-rendered snapshots of the page at CSS pixel size, at most 16384 pixels on a side (Chrome's limit too); a taller page is cut off there. |
| Old-style sessions (`Target.sendMessageToTarget`) | Only flat sessions, which is what current clients use. |

### macOS

The same endpoint, checked with the same tests. What differs:

| | On macOS |
|---|---|
| WebP screenshots | Not available: the system has no encoder for WebP and the engine there contains none. PNG and JPEG work |
| `deviceScaleFactor` | Applied (a Mac's screen has two pixels to one of the page's, and a screenshot is otherwise twice the size asked for). On Linux it is ignored and always 1 |
| What a key does to the text | The system decides it from the user's key bindings and the application's menu, which a synthesized key does not reach: Command+A typed by a client selects nothing, in Chrome as here. Clients say what the key does with `commands` on `Input.dispatchKeyEvent` (Playwright by itself, Puppeteer when the caller passes them), and the page gets the key with those commands |
| Error names | Taken from the system's description of a failure, which is in the user's language. Only English ones are recognised; others come out as `net::ERR_FAILED` |
| Views the endpoint creates | A window that is on no screen. The page behaves as in a visible, focused window. An application that wants to show them supplies its own (`zebkit_cdp_set_create_view_func`), and creates each view with the configuration it is handed |
| Failed loads | The view shows no error page; it stays as it was |
| C API | `zebkit-cdp.h` has the same functions, with `WKWebView` for the view and a string to `free()` for an error |

### Differences from Chrome

Found by running the same checks against both. The first four are on
purpose:

- **A request a web page could forge is refused** (an `Origin` header on an
  HTTP request, a `Host` that is not this machine). Chrome serves these.
- **A dead page answers.** After the page's process has died, Chrome leaves
  `Page.crash`, the commands that were running and the commands sent next
  without any answer until the page is navigated. Here they fail with
  "Target crashed".
- **A dialog nobody answered is dismissed when the client that saw it
  leaves.** In Chrome it stays and blocks the page.
- **A page that is held for the client (`waitForDebuggerOnStart`) has not
  started loading.** Chrome holds it with the navigation under way, and a
  script added then misses the first document.
- A key event without `code` and `windowsVirtualKeyCode` still types: the
  key is worked out from `key` and `text`. Chrome delivers an event with
  no code that does nothing for keys such as Backspace. Clients send both.
- `DOM.resolveNode` and the other DOM commands also take an `objectId`
  where the definition has none.
- An element with both an id and classes is described as `div#id`; Chrome
  adds the classes. Errors are described without their stack.
- Worlds made with an empty name are one world; in Chrome each is new.
- Requests have no priority other than `Medium`.

Smaller differences:

- `Browser.getVersion` reports `Zebkit/<WebKit version>`, and the user agent
  is WebKit's (Safari-like). Sites are served what they serve Safari.
- Response objects carry status, headers and MIME type, not timing, remote
  address or TLS details. `encodedDataLength` is the body size.
- Load progress (`DOMContentLoaded`, `load`) is reported by WebKit for the
  main frame only; for child frames both lifecycle events are sent when the
  frame commits.
- Error descriptions and stack traces are JavaScriptCore's, which word some
  messages differently from V8.
- While a JavaScript dialog is open the page's process is blocked; commands
  to that page wait until `Page.handleJavaScriptDialog`.
- `Target.closeTarget` destroys a page the endpoint created without asking
  it (no `beforeunload`), as Chrome does. A view that belongs to the
  application can only be asked to close, like `Page.close`.
- State set through one session of a page (scripts for new documents,
  bindings, headers, user agent) belongs to the page and lasts until its
  last session is gone.
- `DOM.describeNode` keeps the nodes it gave a `backendNodeId` for alive
  until the document is left; beyond 20000 per document the oldest ids stop
  resolving.
- A page that never answers (script in an endless loop) leaves commands
  without an answer, as in Chrome. Clients have their own timeouts.

## Debugging

`ZEBKIT_CDP_LOG=1` prints every CDP message to stderr; `2` adds the Web
Inspector Protocol messages behind them, tagged with the first characters
of the page's target id.

## Testing

```sh
scripts/cdp.sh slim              # raw protocol checks
scripts/cdp.sh slim --clients    # also Puppeteer and Playwright
scripts/cdp.sh slim --serve      # leave the browser running on port 9333
scripts/cdp-reference.sh         # the raw checks against Chrome itself
```

- `tests/cdp/schema.py` compares every message with the standard
  definition: results and events the endpoint sends, and the parameters the
  tests send. A departure fails the run. Chrome has none; nor does zebkit.
- `scripts/cdp-reference.sh` needs a Chrome or Chromium on the machine
  (`$CHROME`, or on the `PATH`). Run it whenever a check is added or
  changed. Checks marked `@zebkit_only` are left out of it.
- `tests/cdp/protocol.py` speaks CDP directly (a small client on Python's
  standard library) and checks answers against what Chrome gives: discovery,
  access control, evaluation, contexts and worlds, bindings, console,
  navigation events and failures, changing origin, history, screenshots,
  dialogs, mouse, keyboard, DOM geometry (including inside frames), file
  inputs, cookies, targets, sessions, browser contexts and popups. It also
  checks what happens when things go wrong: requests a web page could
  forge, ids chosen to break the bookkeeping, a stopped navigation, a
  crashed page and its recovery, a client that leaves a dialog open, a file
  upload aimed at the wrong element, and the order of input answers. The
  last group came out of the comparison with Chrome: that isolated worlds
  are separate and nodes cross between them, bindings per world, malformed
  messages and wrong parameters, some thirty error codes and messages, how
  objects are described, lifecycle replay, cleared contexts, same-document
  navigation and failed requests.
- `tests/cdp/private.py` runs against an endpoint started without
  discovery.
- `tests/cdp/puppeteer.js` and `tests/cdp/playwright.js` run the same kind
  of script an agent would: connect, open a page, navigate, evaluate, click,
  type, work in frames, take screenshots, go back and forward, handle
  dialogs and popups, upload a file, use cookies and an isolated context.
  `--clients` downloads a pinned Node.js and the two client libraries into
  `.cache/`; they are not part of the engine.

Results are recorded in `docs/PROGRESS.md` and, for each platform, in
`docs/LINUX.md`, `docs/MACOS.md` and `docs/WINDOWS.md`. `profiles/slim-dev.cmake` builds the
engine without link-time optimization; with it a change to `src/cdp` is
running again in about 15 seconds.

## Held to Chrome's definition and Chrome's behaviour (2026-10-10)

Until this point the bridge was written from knowledge of the protocol and
checked only against itself and two client libraries. Chrome's
implementation cannot be compiled against WebKit (it is part of Blink and
V8), so what was taken from it is what can be:

- **Its protocol definition**, vendored unchanged in
  `deps/devtools-protocol` (revision r1716261, 1.6 MiB of JSON, not
  shipped). The endpoint's parameter checks are generated from it, and the
  tests compare every message with it.
- **Its behaviour.** `scripts/cdp-reference.sh` runs the raw checks against
  Chrome. On the first run Chrome failed 15 of the 34 checks, and passed
  the definition check with no departures where zebkit had 10. Some checks
  were wrong; most pointed at zebkit. Side-by-side runs of about 150
  commands and their events found the rest.
- **One more engine patch**, where WebKit lacked what CDP needs
  (`patches/2006`, the same additions Playwright's WebKit has).

What that found, all fixed, each with a check that Chrome passes too:

| Where zebkit differed from Chrome | Before |
|---|---|
| Isolated worlds | Emulated in the page's own world: the page could see and overwrite what a client put there, and a script registered for a world ran in the page. Now WebKit user worlds, separate as in Chrome, with nodes carried between worlds by `DOM.resolveNode` |
| Wrong or missing parameters | Accepted and guessed at (`Runtime.evaluate` without an expression returned `undefined`). Now `-32602 Invalid parameters`, checked against the definition |
| Messages that are not commands (bad JSON, no id, no method, unknown session) | Dropped without an answer, so a client waited for ever. Now answered with Chrome's codes |
| A document changing its own address (fragment, history API) | Not reported at all, so a client's idea of the page's address went stale on single-page sites. Now `Page.navigatedWithinDocument` |
| State set while a new page was still being set up | Lost: a popup did not get the scripts and worlds a client registered in that moment. Found by Playwright's popup test once worlds were real |
| A client that attaches to a loaded page | Was not told the page had loaded. Lifecycle events are now replayed as in Chrome |
| Events with mandatory fields missing or fields Chrome does not have | Dialog events without `frameId`, `navigatedWithinDocument` without its type, object previews without `overflow`, cookies and nodes with fields of WebKit's own |
| How objects are described | Nodes as `<div id="x">` for Chrome's `div#x`; typed arrays, maps, sets, promises, classes, symbols and `-0` with other types and descriptions than Chrome's; the prototype listed as a property |
| About thirty error answers | Other codes and words than Chrome's, or success where Chrome fails (an invalid URL, a malformed object id, focus on what cannot be focused, a cookie with no address, an image format that does not exist, a target that is not there) |
| Navigation and contexts | A `commit` lifecycle event Chrome does not send; contexts reported destroyed one by one where Chrome clears them; `DOM.getDocument` one level deeper or shallower than Chrome's |
| Failed requests | WebKit's sentence for the error and type `Other`; now Chrome's error names (`net::ERR_CONNECTION_REFUSED`) and the request's type |

What zebkit still does differently is listed in `docs/CDP.md` under
"Differences from Chrome".

Limits of this work: the comparison covers the commands the tests and the
side-by-side runs exercise, not all 143 that are implemented; Chrome's
answers were taken from one version (155); and what Chrome does that no
check asks about is still unknown.

## Review for production use (2026-10-10)

A read of all of `src/cdp` and tests aimed at failures, not at the usual
path, found the following. All are fixed and each has a check in
`tests/cdp/protocol.py` unless noted.

| Found | Effect before the fix |
|---|---|
| Every page opened at `about:blank` left a web process running after it closed. An upstream bug in how WebKit hands out its spare process, not in the bridge (`patches/0005`) | 300 pages opened and closed left 303 processes of 100 MiB and more. Now 4, and the application's memory stays flat. Measured by hand; no scripted check |
