# zebkit 0.2.0

Level with Electron 45.2.1 on DOM work, faster on calls between page and host
and on starting, cold and warm; input into every kind of frame; Playwright's own
suite much closer to Chrome's; and a window's handle for the system's dialogs, on
Linux, macOS and Windows.

| Archive | System | Unpacked | `.tar.xz` |
|---|---|---:|---:|
| `zebkit-0.2.0-x86_64-unknown-linux-gnu.tar.xz` | Linux x86-64, glibc 2.17 or newer | 179.7 MiB | 60.9 MiB |
| `zebkit-0.2.0-aarch64-apple-darwin.tar.xz` | macOS, Apple silicon | 157.5 MiB | 47.7 MiB |
| `zebkit-0.2.0-x86_64-pc-windows-msvc.tar.xz` | Windows 10 or newer, x64 | 241.0 MiB | 72.4 MiB |

Windows' archive holds `zebkit_sandbox.lib` (29.4 MiB), which the application's executable
links and does not ship. The Rust crates `zebkit`, `zebkit-rs` and `zebkit-build`
0.2.0 download these archives, each checked against its SHA-256 in
`bindings/rust/zebkit-rs/engines.txt` (the crates moved from `rust/` to
`bindings/rust/`, beside the Python binding).

## What changed since 0.1.0

**Speed** (Linux, `scripts/electron-compare.sh`, `docs/SIZE_AND_SPEED.md`):

| | 0.1.0 | 0.2.0 | Electron 45.2.1 |
|---|---:|---:|---:|
| A call from the page to the host and back, 1 MiB / 16 MiB | 32.1 / 540 ms | 3.4 / 55.6 ms | 4.4 / 71.3 ms |
| DOM, 20,000 elements made and laid out | 410 ms | 280 ms | 278 ms |
| A long document's longest task | 228 ms | 189 ms | 184 ms |
| Text layout, a layout | 9.2 ms | 8.1 ms | 7.6 ms |
| Start cold, to first paint | 4.3 s | 2.3 s | 6.6 s |
| Start warm, to first paint | 120 ms | 116 ms | 236 ms |
| Native `page.screenshot()` | 41.5 ms | 31.5 ms | |
| As an application ships it, uncompressed / `.tar.xz` | 152.3 / 53.5 MiB | 171.2 / 59.4 MiB | 260.5 / 87.1 MiB |

- **Calls between the page and the application** go over each frame's own Mojo
  channel, large ones through shared memory, the page's JSON handed on as it was
  written; `zebkit_call_resolve_json()` takes JSON with its length.
- **Chrome's PGO profile now applies to Blink**: it is recorded from a CFI build,
  and without CFI's checks the compiler dropped it for every function with a
  virtual call. CFI is on for virtual and indirect calls on Linux, never on calls
  into the application's own functions (`patches/1078`); the size-trained
  inliner decides only for code the profile calls cold.
- **A cold start reads the engine into the page cache first**, in one pass on a
  background thread (Linux), as Chrome does on Windows and Android.
- PNG encoding at full speed, V8's and Blink's thread-locals initial-exec.

Every change gained more speed than it cost in size; the package is 12% larger
than 0.1.0's.

**Input into frames.** An application's mouse, wheel and keys reach frames in
processes of their own (another site's, a sandboxed one) through Chromium's input
router, as Chrome's windows do; before, such frames got nothing from an off-screen
view (`patches/1077`, `tests/engine/frames_input.c`).

**A window's system handle.** `zebkit_view_get_native_window()` gives the
top-level window that contains a page (an X11 window, an `HWND`, an `NSWindow*`),
also for a page attached to an application's window or a panel in it; and
`zebkit_view_export_native_window()` names it as the system's portals do,
`"x11:<XID>"` or on Wayland `"wayland:<handle>"` through xdg-foreign. In C, Rust,
Python and host JavaScript.

**Automation.** Playwright's own suite (v1.64.1) against the endpoint:

| | 0.1.0 | 0.2.0 | Chrome |
|---|---:|---:|---:|
| Passed | 3,028 | 4,046 | 4,196 |
| Failed | 1,167 | 149 | 5 |

Among what moved it: Playwright's launch switches, CDP sessions, popups held as
Chrome's, `frameLocator()`, service workers and workers over their own DevTools
sessions, other sites' frames as sessions of their own, HAR and traces as
Playwright writes them, screenshots by Playwright's own capture code, routes
(redirects, CORS preflights, bodies with blobs), the Debugger, coverage, proxies,
client certificates, the virtual WebAuthn authenticator, taps through Chromium's
touch emulator, file choosers.

**Agents.** The MCP server works on pages drawn on a canvas (Google Docs among
them) by coordinates, `page_mouse` and `page_keyboard`, with captures one to one
with them; an outside agent (Claude Code, headless) did real tasks on the open web
with it, and what it ran into is fixed.

**Hooks.** A WebSocket's handshake goes through the network's stages, its Cookie
seen and changeable; client certificates can come from the system's stores (NSS,
the Keychain, Windows' store) behind an engine setting.

**Wayland** (`--ozone-platform=wayland`; X11 stays the default) has run for the
first time: windows and the portal export, in a headless labwc.

## Missing and known issues

- **Playwright's suite is not at Chrome's level.** Left by cause: the recorder
  (14 tests, Playwright's own server code, not ported), frames' edge cases
  (transformed or scrolled iframes, hidden iframes, a worker inside an iframe,
  about 15), trace details (4), full-page screenshots while navigating (2),
  assertions when a page closes (4); client certificates through Playwright's own
  TLS proxy (10), extensions (6) and locale formats outside English and CJK (4)
  are listed differences (`docs/AUTOMATION.md`, section 7).
- **Wayland:** off-screen views beside Wayland windows are refused
  (`zebkit_view_new_offscreen()` returns NULL; making one crashed); attaching to
  an application's window and input methods are not done; not run with a person or
  a GPU. Under `--headless`, and with X11, off-screen views work.
- **Sandbox:** on macOS the helpers crash entering the seatbelt in the test bundle,
  signed ad hoc, so the suite runs with `--no-sandbox` there; on Linux the sandbox
  has not been run on the build machine (no unprivileged user namespaces, no root
  for the set-user-ID helper). Windows' sandbox runs and passes.
- **macOS** builds are not signed with a Developer ID or notarized; `slim-macos`
  has no PGO, and the cold start's pre-read is Linux's only.
- **Windows:** D3D11 frames, the WebAuthn route (`webauthn.dll`), printing through
  the system's dialog and the Node.js tests (Playwright's client, the CDP clients,
  the MCP server) have not run; the network service is unsandboxed, as upstream's;
  a page's first `RTCPeerConnection` asks about the firewall unless the
  application's installer adds a UDP 5353 rule, as Chrome's does.
- **Linux:** no GPU on the build machine (dmabuf frames, hardware compositing);
  X11 windows have Chromium's fake input method.
- **Against Electron:** one process more a page (storage in its own sandboxed
  process, as Chrome); more memory on some sites (YouTube 684 against 583 MB);
  text layout within noise but behind (8.1 against 7.6 ms).
- **Engine aborts:** one SIGSEGV of an engine was seen once during a Playwright
  spec run, with no stack, and not again.
