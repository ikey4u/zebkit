# zebkit 0.1.0

The first release with all three systems: Linux x86-64, macOS on Apple silicon
and Windows x64, one engine and one API on each, built from one tree on Linux.

| Archive | System | Unpacked | `.tar.xz` |
|---|---|---:|---:|
| `zebkit-0.1.0-x86_64-unknown-linux-gnu.tar.xz` | Linux x86-64, glibc 2.17 or newer | 160.8 MiB | 54.9 MiB |
| `zebkit-0.1.0-aarch64-apple-darwin.tar.xz` | macOS, Apple silicon | 157.0 MiB | 47.5 MiB |
| `zebkit-0.1.0-x86_64-pc-windows-msvc.tar.xz` | Windows 10 or newer, x64 | 239.7 MiB | 71.9 MiB |

Windows' archive holds `zebkit_sandbox.lib` (29.4 MiB), which the application's
executable links and does not ship. The Rust crates `zebkit`, `zebkit-rs` and
`zebkit-build` 0.1.0 download these archives, each checked against its SHA-256 in
`rust/zebkit-rs/engines.txt`.

## What is in it

- **Blink as a library.** Chromium 155.0.8059.84's content layer, Blink and V8
  with every JIT tier, as `libzebkit.so.1`, `Zebkit.framework` or `zebkit.dll`,
  with a helper for the child processes. The application keeps its process, its
  main loop and its windows: `zebkit_init()`, `zebkit_pump()`,
  `zebkit_set_wakeup()`, `zebkit_shutdown()`, or `zebkit_main()`; views in the
  engine's windows, inside the application's own (`zebkit_view_attach_native()`:
  an X11 window, an `NSView`, an `HWND`) or off-screen, with frames in shared
  memory, IOSurfaces or dmabufs and input sent by the application.
- **An embedder of its own.** The content shell is out of the engine: windows,
  profiles and the content clients are zebkit's (`docs/ROADMAP.md`).
- **Windows**, new in this release: `zebkit.dll`, `zebkit-helper.exe`, the import
  library and `zebkit_sandbox.lib`, cross-built on Linux with clang-cl. Chromium's
  sandbox is on by default: the application's executable links
  `zebkit_sandbox.lib` and calls `zebkit_win_startup()` first; renderers run at
  untrusted integrity, the GPU process at low, each in a job (`docs/WINDOWS.md`).
  The application's message loop and `HWND`s, off-screen views with a scale each,
  cookies kept with DPAPI, the Rust crate with the sandbox.
- **macOS**: `Zebkit.framework` for Apple silicon, cross-built on Linux; Metal
  compositing, views on an `NSView`, IOSurface frames (`docs/MACOS.md`).
- **Linux**: glibc 2.17 and newer (CentOS 7), checked on CentOS 7's own glibc and
  libraries (`scripts/glibc-test.sh`); Chromium's set-user-ID sandbox helper in
  the package, installed by root with `zebkit-sandbox-install` (`docs/SANDBOX.md`).
- **PDF**: Chromium's PDFium in the engine with a C API (`<zebkit/pdf.h>`) and
  `zebkit.pdf`: rendering, text, search, forms, annotations with appearances,
  redaction, page editing, signatures checked, PDF hooks. **PDF in pages**: a page
  that opens or embeds a PDF shows it as Chrome does, in Chromium's plugin in a
  dedicated renderer, with a small viewer of zebkit's.
- **CDP and Playwright.** Chromium's own DevTools protocol, checked with
  puppeteer-core and playwright-core against Chrome (`tests/engine/cdp_clients.mjs`);
  **Playwright's API natively** (`<zebkit/automation.h>`, Python's
  `zebkit.automation`, Rust's `zebkit::automation`): its commands run inside the
  engine, 3 to 10 times faster than Playwright over CDP for what does not wait
  for a frame; and Playwright's own protocol on a WebSocket, so that its clients
  drive zebkit unchanged with `chromium.connect()` (`docs/AUTOMATION.md`).
- **An MCP server**, `tools/zebkit-mcp`: the engine's capabilities as MCP tools for
  AI agents, over standard input and over HTTP: pages, PDF, files, media, native
  windows, within the bounds whoever runs it sets (`docs/MCP.md`).
- **Hooks for the engine's decisions** in C, Rust, Python and JavaScript:
  permissions, navigation, popups, dialogs, downloads, certificates, settings at
  run time, and **network hooks**: requests and responses held or observed by URL,
  type, frame and stage, answered with bytes, a file or a stream, bodies as they
  pass, the headers the network itself adds (`docs/HOOKS.md`).
- **Libraries and services for applications**: 17 C libraries inside the engine
  under `zebkit_vendor_*` (FreeType, LevelDB, zlib, SQLite, BoringSSL, ...), Skia
  drawing (`<zebkit/canvas.h>`), HarfBuzz shaping (`<zebkit/text.h>`), the engine's
  FFmpeg, media capture of what a page plays, `zebkit-js` without Node.js.

## Size and speed against Electron 45.2.1

`scripts/electron-compare.sh`, 2026-11-02, Linux x86-64, one harness and two thin
hosts (`docs/SIZE_AND_SPEED.md`, `docs/reports/electron-compare.md`):

| | zebkit | Electron 45.2.1 |
|---|---:|---:|
| Size as published, uncompressed / `.tar.xz` | 160.8 / 54.9 MiB | 273.4 / 88.7 MiB |
| Size as an application ships it | 152.3 MiB | 260.5 MiB |
| Start warm, to first paint | 120 ms | 232 ms |
| Start cold, to first paint | 4720 ms | 6337 ms |
| Memory, a blank page | 173 MB | 249 MB |
| A 756-page PDF: CPU loading / memory | 0.73 s / 253 MB | 1.59 s / 400 MB |
| Ten sites: CPU loading / memory | 18.4 s / 4362 MB | 24.8 s / 5044 MB |
| Text layout, a layout | 9.2 ms | **7.8 ms** |
| DOM, 20,000 elements made and laid out | 410 ms | **281 ms** |
| A call from the page to the host and back, 64 bytes / 1 MiB | 0.4 / 32.1 ms | **0.1 / 4.3 ms** |

zebkit is smaller, starts faster and costs less memory and less CPU while loading;
it loses text layout, the DOM workload and calls between the page and the host,
shown in bold. On macOS it starts warm in 135 ms against 229 and costs 5 to 18%
less memory on local pages, and loses layout by 7%, the JavaScript and DOM page
by 15% and calls to the host by 7 to 22 times.

## Tested for this release

The archives above, built from this commit's tree (Chromium 155.0.8059.84 with
`patches/series` and nothing else), 2026-11-02:

| | Result |
|---|---|
| Linux, `scripts/engine-test.sh slim` | no failure, no section skipped; 2,591 of 2,591 checks in the sections that print a total |
| Linux, `scripts/glibc-test.sh slim` (CentOS 7's glibc 2.17 and libraries) | no failure; 451 of 451 checks in the sections that print a total |
| Linux, `cargo test` in `rust/` | 11 passed, none failed |
| Linux, `scripts/automation-bench.sh --check` | passed: no native command slower than Playwright over CDP |
| Linux, Playwright's own suite (`scripts/playwright-suite.sh`, v1.64.1, 5,262 tests) | 3,028 passed, 1,167 failed, 1,067 skipped; of the failures 580 listed with a reason, 587 not explained (197 timeouts, 8 with the client told the page or browser closed); no engine exit |
| macOS 27.0.1, Apple M4, the suite cross-built on Linux | no failure; 1,915 of 1,915 checks in the sections that print a total |
| Windows 10 19045, 2 CPUs, the suite cross-built on Linux | one failure, in a test (below); 1,868 of 1,868 checks in the sections that print a total |

The Windows failure was `hook-javascript-page`, mode `file-close`: the file
chooser's handler closes the view, and when the chooser's request reached the
browser before the reply to the evaluate that clicked, that call failed with "the
page target was detached", as CDP fails a detached target's commands, and the test
took the reply for granted. It failed in 3 of 6 runs on Windows and in none on Linux
or macOS. The C, Python and JavaScript tests now accept that answer in that mode
(the commit before this one); the fixed tests passed 8 of 8 runs on Windows and 3 of
3 on the Mac. Nothing in the engine changed.

Not run: on macOS and Windows, the tests that need Node.js (Playwright's client
against the endpoint, the CDP clients, the MCP server; on Windows also certificates
over HTTP/2), since neither test machine has it; on the Mac, 6 pixel checks of
`native-parent` (no picture of the window) and WebRTC's loopback between two
peers (they did not connect: macOS's Local Network permission is suspected); on
Windows, its WebAuthn route (below). Nearly all of each suite runs with
`--no-sandbox`; on Windows the sandbox has sections of its own
(`win-smoke-sandbox`, `win-host-sandbox`, `win-native-parent-sandbox`), which passed.

## Missing and known issues

Windows:

- **D3D11 frames have never run.** `ZEBKIT_BUFFERS_GPU` asks for shared D3D11
  textures; the test machine's display adapter has no D3D shared images, so frames
  came in shared memory there. Untested on a real GPU.
- **Windows' WebAuthn route** (`webauthn.dll`) has never been tried: the test
  machine's `WebAuthNGetApiVersionNumber()` is 0. WebAuthn with the virtual
  authenticator passes.
- **The tests that need Node.js** (Playwright's client against the endpoint, the
  CDP clients, the MCP server, certificates over HTTP/2) have not run on Windows.
  The MCP server's standard input on Windows is untried.
- **JavaScript dialogs** in a window with no handler (`alert()`, `confirm()`,
  `beforeunload` as a message box) have not been run.
- **The network service is not sandboxed**, as upstream's default
  (`kNetworkServiceSandbox` is off): a broken renderer's next step is a process with
  the user's rights and every site's cookies (`docs/WINDOWS.md`).
- **The firewall asks about `zebkit-helper.exe`** the first time a page makes an
  `RTCPeerConnection`: WebRTC's mDNS binds UDP 5353. An application's installer should
  add an inbound rule for UDP 5353 for `zebkit-helper.exe`, as Chrome's installer does
  for Chrome; `--disable-features=WebRtcHideLocalIpsWithMdns` binds nothing, but shows
  pages the machine's address instead of a `.local` name.
- Tested on one machine: Windows 10 19045, two CPUs, VMware's display adapter.
  Windows' own input in attached views, `zebkit.ui` beyond its script's test, printing
  through the system's dialog and views with windows beside off-screen views in one
  process (Windows still needs `--headless` for off-screen views) are not done.
- **The Rust crate's download on Windows** has not been tried, and it calls
  `sha256sum`, which a Windows without Git's tools lacks; set `ZEBKIT_DIR` to the
  unpacked archive instead.

macOS:

- **The sandbox on macOS**: in the test bundle, signed ad hoc, the helpers crash at
  their start inside the seatbelt ("the sandbox could not be entered"), so the suite
  runs with `--no-sandbox` and a PDF has not been seen parsing inside the seatbelt
  (`docs/MACOS.md`). Not looked into.
- WebRTC between two peers did not connect on the Mac (above); real input, input
  methods, the real Keychain, a real camera and microphone need a person and were not
  run. Not signed with a Developer ID, not notarized. `slim-macos` is built without
  PGO.

Linux:

- **The sandbox has not been run on the build machine**: it allows no unprivileged
  user namespaces and has no root to install the set-user-ID helper, so every suite
  ran with `--no-sandbox`.
- **Input methods**: a window under X11 has no system input method (ibus, fcitx):
  Chromium's fake context, as before. Off-screen views compose through the
  application. Only X11 was tested.
- **Wayland has never been run**, nor a GPU on Linux (dmabuf frames, hardware
  compositing): the build machine has neither.

Everywhere:

- **Playwright's own suite is not at parity**: 587 failures that neither the
  expected-failures list nor Chrome explains, 197 of them timeouts (above,
  `docs/AUTOMATION.md`, section 7).
- **Losses against Electron 45.2.1** (table above): Electron lays text out in 15%
  less time and 18% less of the renderer's CPU (the build's code speed,
  `docs/SIZE_AND_SPEED.md`); it runs the DOM workload in 31% less time and the long
  document's longest task in 24% less; calls between the page and the host are 4
  times faster in Electron for 64 bytes and 7.5 times for 1 MiB (`zebkit.app` goes as
  JSON text, with copies on both sides); zebkit runs one process more a page.
- **Native `page.screenshot()` is slower than on 2026-10-27**: 40.1 ms in this
  release's `scripts/automation-bench.sh`, against 29.9 ms then (and 33.4 for Chrome
  156 over CDP). Not investigated.
- The MCP server has been driven by its own scripted run and the official client,
  not yet by an outside agent on the open web.
