# zebkit 0.5.0

Every binding has the whole C API, and Go is a binding of its own; X11
windows have a real input method; a page can be searched as Chrome's find
bar searches it; each download says how it ended. Every archive carries the
license and the notices of what is inside it.

| Archive | System | Unpacked | `.tar.xz` |
|---|---|---:|---:|
| `zebkit-0.5.0-x86_64-unknown-linux-gnu.tar.xz` | Linux x86-64, glibc 2.17 or newer | 186.4 MiB | 62.6 MiB |
| `zebkit-0.5.0-aarch64-apple-darwin.tar.xz` | macOS, Apple silicon | 155.5 MiB | 42.0 MiB |
| `zebkit-0.5.0-x86_64-pc-windows-msvc.tar.xz` | Windows 10 or newer, x64 | 255.0 MiB | 75.6 MiB |

The archives are 2.2 to 2.4 MiB larger unpacked than 0.4.0's (184.1, 153.3
and 252.6 MiB) and within 0.2 MiB of them compressed (62.5, 41.8 and
75.7 MiB): most of it is the third-party notices each archive now carries
(2.0 MiB in the Linux package, `docs/reports/slim.md`), which compress well.

The Rust crates `zebkit`, `zebkit-rs` and `zebkit-build` 0.5.0 download these
archives, each checked against its SHA-256 in `bindings/rust/zebkit-rs/engines.txt`.
The Python binding `zebkit` 0.5.0 is the binding alone; its engine is this
release's archive. The Go module is tagged `bindings/golang/v0.5.0`
(`go get github.com/ikey4u/zebkit/bindings/golang@v0.5.0`); its engine, too, is
this release's archive.

## What changed since 0.4.0

**A Go binding.** `bindings/golang`, on cgo: all of the C API, on Linux,
macOS and Windows. Windows programs are cross-built with its `cmd/zebkit-cc`,
the only route tested; a C initializer (`.CRT$XCU`) calls
`zebkit_win_startup()` before the Go runtime starts, so a Go program is the
engine's sandboxed children itself. Its checks
(`internal/check*`) pass on all three, on macOS and Windows with the sandbox
on (`bindings/golang/README.md`). It follows Go's conventions: package
functions put the verb first (`SetAppBadge`, `RegisterScheme`, `StopCDP`),
objects come from `New...`, what the engine can refuse returns an `error`
(`ErrRefused`, `ErrClosed`, `ErrNotStarted`) and constructors
`(value, error)`; JSON goes in as text or as any value `encoding/json`
encodes; a call off the engine's thread panics, except what C lets any
thread call. `zebkit.BindingVersion` is the engine version it is made for.

**Every binding has the whole C API.** Python and host JavaScript
(`zebkit-js`) gained what they lacked: contexts, off-screen views with their
frames and input, `<zebkit/page.h>`, media capture and taps, the rest of PDF,
Playwright's API inside the engine and the rest of a view. Rust gained
contexts (`zebkit::Context`). `scripts/check-bindings.py` checks that each
binding reaches every exported function. `--zebkit-cookie-key-file` gives
`zebkit-js` a cookie key from a file.

**Find in page** (`<zebkit/page.h>`), on Chrome's own find
(`FindTabHelper`): `zebkit_view_find()`, `zebkit_view_stop_finding()`,
`zebkit_view_on_find()` and `zebkit_view_find_result()`. It looks in the main
document, in every frame (other sites' too) and in open and closed shadow
trees; it gives the count and the active match, goes to the next and the
previous around the end, matches case or only highlights. Over CDP, on a
page's session: `Zebkit.find`, `Zebkit.stopFinding`, `Zebkit.getFindResult`
and `Zebkit.findResult` events. In Rust, Python, Go and host JavaScript
(`docs/API.md`; `tests/engine/find_in_page.py`).

**How a download ended** (`<zebkit/hooks.h>`). Each report to
`zebkit_view_on_download_progress()` has its `outcome` (`in-progress`,
`complete`, `cancelled`, `failed`), `savedPath` once complete, the `guid` CDP
knows it by, and for one cancelled or failed an `error` with its category,
Chromium's interrupt reason as `code` and `name`, Chrome's message and whether
it may resume. CDP clients get the same reports as `Zebkit.downloadProgress`
after `Zebkit.setDownloadEvents`, since `Browser.downloadProgress` says
`canceled` for a failure too (`docs/HOOKS.md`;
`tests/engine/download_outcomes.py`).

**Dialogs of native Playwright actions stay with their holder.** Playwright's
API inside the engine (`<zebkit/automation.h>`) dismissed every held dialog
its client had no listener for, one held for the application, by
`ZEBKIT_DIALOG_POLICY_HOLD` or for a CDP client among them, so that a native
click's `confirm()` closed before its holder saw it. It now dismisses only
what it alone holds; the others stay open for their holder, are told to the
automation client as `BrowserContext.dialog` and `dialogClosed`, and the
action ends once the dialog is answered (`tests/engine/automation_dialogs.py`).

**X11 windows: a real input method.** The engine is a client of IBus itself
(`src/engine/ime_ibus_linux.cc`): ibus-daemon, or fcitx5's IBus frontend,
found by `IBUS_ADDRESS` or the file ibus-daemon writes; composition drawn in
the page, candidates at the caret, password fields left alone. Before, X11
windows had none, and Chinese, Japanese or Korean could not be typed
(`tests/engine/input_method.py`).

**Chrome's focus ring.** A focused field had Blink's placeholder default, an
orange ring; zebkit sets Chrome's.

**A license, and the notices in every archive.** `LICENSE` holds the GNU
LGPL 2.1 (`LGPL-2.1-or-later`), which the crates and the Python package
already declared; each crate, the Python package, the Go module and
`zebkit-mcp` carry a copy (`scripts/check-bindings.py` checks that it is
one). Every package and release archive has `LICENSE`, `NOTICE` (the
version, Chromium's version, the tag its source is at) and
`THIRD_PARTY_NOTICES.txt`, made by `scripts/third-party-notices.py`
(`docs/LICENSING.md`). 0.4.0's archives have none of them.

**zebkit-mcp: local addresses guarded.** Besides the names and addresses
`--allow-origin '*'` leaves out, an http or https response to a public name
from an address of this machine, a local network or a range the IANA
registries mark not globally reachable (DNS rebinding) is refused, under `*`
and under named origins. The guard stops the page reading the answer, not
the request being sent: Chromium's Local Network Access stops a public
page's requests to local addresses before they go, but not its top-level
navigation (`docs/MCP.md`, "What is sent before the refusal").
`--allow-local-network` allows local answers with named origins;
`--allow-origin '*'` with it does not start, unless
`--allow-local-network-for-any-origin` is given, for a server behind a proxy
that resolves names. More of Chromium's switches are refused after `--`,
among them `--ip-address-space-overrides` (`docs/MCP.md`, "Running it").

**Documents.** `docs/HOOKS.md`, renamed from the hooks' roadmap, is the design
and the reference of the hooks; the investigations of Google's sign-in,
cookies across restarts and passkeys are in `docs/notes/`. `SECURITY.md` and
`CONTRIBUTING.md` are new.

## Defaults that changed

- **Clipboard writes granted.** `navigator.clipboard.writeText()` and
  `write()` after a click (`clipboard-write`) are granted by default, as
  Chrome grants them. Reading the clipboard (`clipboard-read`) stays denied
  unless the application permits it.
- With no home directory to keep a profile in, the engine uses a private
  temporary one, deleted as it stops; a `--user-data-dir` that cannot be made
  fails the start (exit code 1).

## Breaking changes

### C

An application built against 0.4.0's headers needs these looked at; the
functions added are named among them:

- `zebkit_post_task()`, `zebkit_post_delayed_task()` and `zebkit_view_attach()`
  return `bool`: false, and the task never run, for a NULL function, before
  the engine has started and once it has stopped; false for an attach to a
  NULL or closed view, to the view itself or to a parent with no window.
- Every `zebkit_view_*()` function is safe on a closed view, on NULL and off
  the engine's thread: it does nothing and returns its failure value. A
  callback the engine owes a view (an evaluation, a capture, a PDF, a media
  list, a drag's answer) is called exactly once, with an error if the view
  closes first, before its `on_close`. An attached view closes with its parent.
- `zebkit_context_close()` posts the closing, as `zebkit_view_close()` does,
  so it may be called from any callback; the profile is freed when its pages'
  processes have gone.
- `zebkit_call_resolve(call, NULL)` resolves the page's promise with
  `undefined`; a call may be answered from any thread.
- A tray icon's clicks and its menu's choices reach the application in a
  task of their own, where it may close the tray or change the menu.
- The application menu's JSON is plain JSON, as the tray's and the Dock's:
  no comments or trailing commas; its functions are for the engine's thread
  and refuse others with an error.
- A page's PDF documents (`zebkit.pdf`) belong to the document that opened
  them (or to the script): another document, even of the same origin, cannot
  use them.
- `zebkit.fs`'s root, the directory granted, is resolved (its links followed)
  for each call, not once.
- A service worker's `clients.openWindow()` opens a view only through a page
  of the worker's own origin in the same context, with that view's popup
  options, handler and popup policy; none without such a page.
- `zebkit_native_window_export_func` is
  `(zebkit_view *view, const char *handle, void *data)`, where it was
  `(void *data, const char *handle)`, and is called with NULL, the view still
  valid, before `on_close` when the view closes first.
- **One outcome for every asked hook** (`<zebkit/hooks.h>`'s top comment,
  `docs/HOOKS.md`, "The outcome"): the request's metadata with `state`, what
  was decided in the past tense, and `reason`.
  - Navigation: `state` is `continued`, `cancelled` or `redirected`; it was
    `settled`, with `action` (`continue`, `cancel`, `redirect`), which is gone.
  - HTTP authentication: `state` is `provided` or `cancelled`; the `provided`
    field is gone.
  - Downloads: what the function decided is told to the new
    `zebkit_view_on_download_result()`, `state` `saved` (it was `save`) or
    `cancelled`; `zebkit_view_on_download_progress()` no longer gets it.
  - The network: a held request's outcome is `continued`, `blocked`,
    `redirected` or `fulfilled`, where it was `answered`.
  - Reasons: `opener-closed` for an orphaned popup's certificate and sign-in
    requests (they said `handler-changed`). Requests the engine's stop ends
    are refused and never told (certificates said `cancelled`), and those of
    a closing view end without an outcome: `on_close` is the signal.
  - A popup's outcomes go to its opener's result function while the opener
    decides for it.
- Console and network events count what they dropped as `dropped`, a number;
  it was a decimal string.
- A serial device chooser's `filters` have `vendorId` and `productId`, as USB's
  and HID's do; they were `usbVendorId` and `usbProductId`.
- A shared or service worker's WebSocket is decided by its own profile's
  network policy (`patches/1086`), and its `workerType` is `shared` or
  `service`, where it was `shared-or-service`.
- `zebkit_open_external()` and `zebkit_show_in_folder()` ask the system off the
  engine's thread and return true once the request is valid and handed over;
  `zebkit_open_external_async()` and `zebkit_show_in_folder_async()` tell how
  it went.
- `zebkit_cdp_listen()` while CDP is served at another address or port is an
  error; `zebkit_cdp_listen_async()` serves CDP without waiting on the engine's
  thread. `zebkit_automation_listen()` off the engine's thread tells its function
  the error.
- New: `zebkit_view_new_offscreen_ex()`, the reason a view was not made;
  `zebkit_view_on_process_gone()`, Electron's `render-process-gone`;
  `zebkit_view_on_responsiveness()`, its `unresponsive` and `responsive`;
  `zebkit_call_free()`, a call dropped unanswered, its promise rejected.
- Power events' `lock` and `unlock` come from the system's notifications
  (macOS's, Windows' session changes, Linux's screen saver over D-Bus), not a
  poll; a Linux desktop without a screen saver service tells none.
- A refused hook reply says why: `char **error` where the reply takes one,
  `request.error` in host JavaScript.

Added, not breaking: the find functions of `<zebkit/page.h>`; `outcome`,
`savedPath`, `guid` and `error` in a download's reports; `remoteAddress` in
the network hook's `response` and `headersReceived` metadata, the IP address
the response came from (`docs/HOOKS.md`).

### Rust

- `FrameBuffer` is `#[non_exhaustive]`, has `D3D11(handle)` for a Windows
  texture, a `handle` in `SharedMemory` (the file mapping on Windows), and
  `Dmabuf`'s planes as slices the frame lends (`&[i32]`, `&[u32]`), with
  `Frame::format()` (`PixelFormat`).
- Calls that can be refused have `try_*` forms returning `Result`
  (`View::try_new`, `View::try_attach`, the hook requests' `try_respond` and
  the like); handlers have `clear_*` methods.
- Engine buffers are `zebkit::Bytes`, which holds the engine's own buffer and
  frees it on drop, where they were `Vec<u8>`: `canvas::Canvas::pixels` and
  `png`; `services::{compress, decompress, aes_gcm_seal, aes_gcm_open,
  encode_image}` and `services::Image.rgba`, which is also what
  `pdf::Document::render` gives (a tile is `RenderOptions.tile`); and
  `pdf::Document::{signature_contents, image_data, attachment, save,
  annotation_file, export_annotations}`.
- What the engine lends for a call is borrowed: `View::capture` and
  `View::print_to_pdf` give `Result<&[u8], Error>`; `services::Response<'a>.body`
  is `&[u8]`; `scheme::Request::body()` is `Option<&[u8]>`; `CursorImage<'a>`,
  `Drag<'a>`, `DragImage<'a>` and `automation::Pixels<'a>` borrow their pixels.
- Renamed: `stop_frames`, `stop_dialogs` and `stop_find_results` are
  `clear_frame_handler`, `clear_dialog_handler` and `clear_find_handler`;
  `media_capture_start` is `media_capture`; `zebkit::environment()` and
  `zebkit::capabilities()` are in `zebkit::system`.
- `View::new_offscreen` and `Context::new_offscreen_view` return
  `Result<View, Error>`, the engine's reason, where they returned `Option`.
- `View::set_user_agent_override` returns `bool`, the engine's rule: `false`
  only for a closed view, and `done` is then never called; otherwise `done` is
  called exactly once, after the call returns, with `{}` or the error (invalid
  options, a NUL in them, among them).
- `View::find` returns `Result<i32, Error>`; `automation::Page::wait_for_event`
  returns the `ListenerId`, so that a wait for an event that never comes can
  be removed.
- `zebkit::json::Value::parse` is strict RFC 8259, refuses nesting deeper than
  128 levels, and keeps the later of a key named twice.
- `automation::Page::add_init_script`'s `done` gets `Result<Disposable, Error>`;
  `Disposable::dispose` removes the script (`Page.removeRegistration`).
- `Call` is `Send`, since an answer may come from any thread; one dropped
  unanswered is freed with `zebkit_call_free()`, and the page is told "the
  application dropped the call".
- New shapes: `on_dialog_closed` takes `FnMut(u64, bool, Option<&str>)`;
  `on_find` takes `FnMut(&FindResult)`.
- `automation::Locator`'s actions (`click`, `dblclick`, `hover`, `check`,
  `uncheck`, `fill`, `press`, `press_sequentially`, `set_input_files`,
  `wait_for`) answer `Result<()>` where they answered `Result<String>`;
  `Locator::wait_for` takes `Option<&str>` where it took `&str`;
  `Locator::get_attribute` answers `Option<String>`.
- `automation::Page::screenshot_with` is gone (`screenshot(options)`), and
  `Page::screenshot_pixels` takes its options as a `Value`, not a `&str`.
- `automation::BrowserContext::close` answers `Result<()>` where it answered
  `Result<String>`.
- `FrameBuffer::Unknown(i32)` is a new variant, for a kind of buffer this
  binding does not know; `FrameBuffer` and `PixelFormat` are
  `#[non_exhaustive]`.
- The crates declare `rust-version = "1.82"`; 0.4.0's declared none.
- zebkit-rs: `zebkit_native_window_export_func` is
  `fn(*mut zebkit_view, *const c_char, *mut c_void)`, the C callback's order,
  where it was `fn(*mut c_void, *const c_char)`; `View::export_native_window`
  is unchanged.
- `automation`: `commands()` gives `Vec<String>`; `Page::new` installs the page's
  own event handler and `Page::on_event` is gone (`on`, `on_protocol_event`, or the
  module's `on_event`); `Page::screenshot(options)` returns the bytes;
  `Page::press`, `type_text` and `mouse_click` are `keyboard()` and `mouse()`;
  `BrowserContext::new(&str)` is `new_context(Value)`; `get_by_role(role,
  RoleOptions)`, and the other `get_by_*` take `impl Into<Text>`; `command(method,
  params: Value)` answers `Result<Value>`; results are typed (`goto` gives
  `Option<Response>`, `count` a `usize`, `is_*` a `bool`, `text_content` an
  `Option<String>`, `evaluate(expr, arg)` a `Value`); `select_option(&[SelectOption])`
  gives `Vec<String>`; `filter_has_text` is `filter(&Filter)`; `content_frame()`
  gives a `FrameLocator`; `Locator::expect` is `automation::expect(&locator)`.
- Added: Playwright's types in `automation` as Python has them (events, routes,
  `Request`, `Response`, `Route`, `Dialog`, `Download`, `Keyboard`, `Mouse`,
  `Clock`, `Tracing`, `APIRequestContext`, `FrameLocator`, `ElementHandle`,
  `BrowserContext`, `expect`); `zebkit::json::Value`, so that the crate still
  has no dependencies; typed `View::dialogs()` and `Call::args()`; the C
  functions above (`on_download_result`, `on_process_gone`,
  `on_responsiveness`, `system::open_external_async`,
  `system::show_in_folder_async`, `cdp::listen_async`), each handler with its
  `clear_*_handler`; `automation::Disposable`.

### Python

- A call off the engine's thread raises `zebkit.Error` instead of reaching
  the engine.
- `zebkit.UNDEFINED`, returned from a bound function, resolves the page's
  promise with `undefined`; network events have `header_list`, every header
  in order; `Frame.memory()` gives a shared-memory frame's pixels without a
  copy.
- `View.on_popup` takes `function(bounds_or_None)`, as Rust and Go do; it took
  `function(shown, bounds)`.
- Added: `automation.call(view, method, params)` and `automation.on_event(view,
  function)`, Playwright's protocol by name; `command()` on `Page`, `Frame`,
  `Locator`, `ElementHandle` and `BrowserContext`; `Page.on_protocol_event`,
  `Locator.content_frame`, `BrowserContext.id`; the C functions above
  (`View.on_download_result`, `on_process_gone`, `on_responsiveness`,
  `zebkit.open_external_async`, `show_in_folder_async`,
  `cdp_listen_async(address, port, function)`); `View.bind_call(name, function)`
  with `zebkit.Call` (`args`, `origin`, `resolve`, `resolve_json`,
  `resolve_undefined`, `reject`, `answered`, `close()` to drop it unanswered
  now), answerable from any thread, a call dropped unanswered rejecting the
  page's promise; `zebkit.FindResult`, what `find_result()` and `on_find()`
  give; `Future.cancel()` in `zebkit.automation`, which also removes what it
  waited for (`wait_for_event()`'s listener); `zebkit.automation.Disposable`,
  which `Page.add_init_script` returns.
- `View.offscreen` raises `zebkit.Error` with the engine's reason.
- `set_user_agent_override`: invalid options return True and are told once,
  after the call returns; False, its function never called, only for a closed
  view or the wrong thread.
- `View.find()` raises `zebkit.Error` for text with a NUL, text that is not
  UTF-8, or the engine's refusal.
- Fixed: `goto`, `reload`, `go_back` and `go_forward` give a `Response` whose
  `body()` works; `requestfinished` and `requestfailed` give the whole request.

### Go

The first release of the Go binding: nothing to break. Programs written
against `@main` before the rework to Go's conventions (above) need its new
names and error returns.

- `View.Find(text, flags)` returns `(int, error)` and takes a `FindFlags`.
- On Windows `zebkit_win_startup()` runs from a C initializer, before the Go
  runtime, not from `init()`: a renderer's WebAssembly traps no longer reach
  Go's exception handlers (`bindings/golang/win_sandbox.go`).
- Added: the C functions above (`OnDownloadResult`, `OnProcessGone`,
  `OnResponsiveness`, `OpenExternalAsync`, `ShowInFolderAsync`,
  `ListenCDPAsync`); `Canvas`'s methods have their documentation.

- The typed Playwright API is the new package
  `github.com/ikey4u/zebkit/bindings/golang/automation`, with the features of
  Rust's `zebkit::automation` and Python's `zebkit.automation`: pages and
  frames, locators and frame locators, `page.On(kind, ...)`, `RemoveListener`
  and `WaitForEvent`, routes (globs and `*regexp.Regexp`), `Request`,
  `Response` (with the body) and `Route`, `ExposeFunction` and
  `ExposeBinding`, dialogs, file choosers, downloads, workers, the console,
  keyboard, mouse, touch screen, clock, tracing and HAR, `APIRequestContext`,
  JS and element handles, contexts with their cookies, permissions and pages,
  and `Expect` assertions; `AddInitScript` gives a `Disposable`. Every method
  runs on the engine's thread and answers once, there, as `func(T, error)`, or
  `func(error)` for a command that answers nothing.
- Breaking for programs on `@main`: the root package's `Page`, `Frame`,
  `Locator`, `BrowserContext`, `NewPage` and `NewBrowserContext` moved to the
  `automation` package in new shapes. The low level stays in the root package
  (`CallAutomation`, `CallAutomationPixels`, `View.OnAutomationEvent`,
  `ViewByPageID`, `ListenAutomation`).

  | Before (root package) | Now |
  |---|---|
  | `zebkit.NewPage(view)`, `Page{View}` | `automation.NewPage(view)`, `page.View()` |
  | `Page.OnEvent` (raw JSON) | `page.On(kind, func(*PageEvent))`, `RemoveListener`, `WaitForEvent`, `OnProtocolEvent` (raw) |
  | `Page.Press`, `TypeText` | `page.Keyboard().Press(key, delay, done)`, `.Type(text, delay, done)` |
  | `Page.MouseClick(x, y)` | `page.Mouse().Click(x, y, options, done)` |
  | `GetByRole(role, name)` | `GetByRole(role, automation.RoleOptions{Name: ...})` |
  | `Locator.FilterHasText(t)` | `Locator.Filter(automation.Filter{HasText: t})` |
  | `Locator.Expect(expr, params)` | `automation.Expect(l).ToHaveText(...)` and the like, or `.Check(expr, options, done)` |
  | `Page.Frame(id)` | `page.FrameByID(id)` |
  | `Goto` answering `json.RawMessage` | answering `*Response` |
  | `EvaluateFunction(fn, arg)` answering `{"value": ...}` | `Evaluate(expr, arg)` answering the value |
  | `Page.Screenshot(path)`, `ScreenshotWith(options)` | `Screenshot(options, done func([]byte, error))`, `path` among the options |
  | a locator action's `done(json.RawMessage, error)` | `done(error)` |
  | `TextContent`, `GetAttribute` answering `string` | answering `*string` |
  | `WaitFor(state)` answering `json.RawMessage` | `done(error)`; `""` is visible |
  | `AriaSnapshot` answering `{"snapshot"}` | the YAML `string` |
  | `SelectOption(valueOrLabel)` | `SelectOption([]SelectOption{...})`, answering the values selected |
  | `zebkit.BrowserContext{ID}`, `NewBrowserContext` | `automation.NewContext(options, done)`, `ctx.ID()`, `Close(done func(error))` |
  | `View.OnFind(func(map[string]any))`, `FindResult() (map, error)` | `OnFind(func(zebkit.FindResult))`, `FindResult() (zebkit.FindResult, error)` |

- With no dialog or file-chooser listener a dialog is dismissed (a
  `beforeunload` one accepted) and a chooser cancelled; removing the last
  listener turns the subscription off.
- `View.SetUserAgentOverride` returns an error only when `done` will never be
  called (a closed view, the engine's refusal); options it cannot read are
  told once, to `done`.
- New: `zebkit.IsEngineThread()`.

### Host JavaScript

- `zebkit-js` keeps a view's hook until the task that closed the view has
  ended, and reports a promise rejected without a handler only once the
  promise jobs have run (it reported a rejection handled in the same turn as
  uncaught).
- The outcome fields of C above, in the same events: `navigation-result`'s and
  `http-auth-result`'s `state`, downloads' decisions in `view.onDownloadResult()`.
- Added: `zebkit.cdp.listenAsync()`, `zebkit.openExternalAsync()`,
  `zebkit.showInFolderAsync()`, `view.onDownloadResult()`, `view.onProcessGone()`,
  `view.onResponsiveness()`, and `request.error`, why a hook's reply was refused.
  The told events (console, popup-blocked and the results) are registered only
  when a script listens for them.

### zebkit-mcp

- New switch `--allow-local-network`; without it a public name answered from a
  local address is refused (`refusedByBounds` `{"what": "address"}`,
  `ERR_ADDRESS_UNREACHABLE`). The guard holds every http and https response of
  a page, of `net_fetch` and of the device flow at the network hook's
  `response` stage; one without an address is refused; one from the HTTP cache
  is checked by the address it was fetched from; `data:` and `about:` pass,
  and `blob:` by its inner URL.
- The addresses it counts as local are the IANA special-purpose registries'
  not globally reachable ones: besides loopback and the private ranges, the
  documentation and benchmarking ranges, Teredo `2001::/32`, the rest of
  `2001::/23` but its global blocks, `64:ff9b:1::/48`, SIIT, `192.88.99/24`,
  `100::/64`, `5f00::/16`, `192.0.0/24` but `.9` and `.10`; the resolver's
  rules under `*` have the same.
- `--allow-origin '*'` with `--allow-local-network`, in either order, does
  not start (exit 2); the new `--allow-local-network-for-any-origin`, which
  implies `--allow-local-network`, allows it, for a server behind a proxy that
  resolves names itself.
- Pages open no WebSockets: `ws:` and `wss:` are refused at the request
  stage.
- `--ip-address-space-overrides` after `--` is refused.

## Fixes

- A closing view's automation events no longer reach data an application
  freed; the Playwright endpoint still gets a page's `Page.close`.
- Off-screen GPU buffers fall back to shared memory where they cannot be made.
- Hooks, trays, notifications, the automation endpoint and host JavaScript
  free what they own when its owner goes.
- Every asked hook settles its requests the same way: a per-view cap, the
  deadline for each, refused at the engine's stop; a popup gets all twelve
  of its opener's hook deadlines, not four.
- The sign-in dialog and the client certificate picker close with their
  request. On macOS a page's JavaScript dialog is a sheet on its own window,
  one per page, titled with its origin; on Windows every dialog is the views
  dialog, as on Linux, so that a page's dialogs close with it.
- The macOS context menu runs from a task of its own; a Windows window gets
  the taskbar's badge and progress again when it is shown or activated.
- A share request ends when its document goes; a refused notification on
  macOS closes.
- The off-screen IOSurface copy on macOS runs off the engine's thread.
- `zebkit-mcp` writes its address and its generated token in one write, and
  checks files on Windows.

## Tests and releases

- `mise run check` (`scripts/check.sh`) runs what a release is published
  after: the static checks (also alone, `mise run check:static`: `bash -n`, Python
  syntax, `scripts/check-bindings.py`, `scripts/check-view-guards.py` and
  `scripts/check-reports.py`), `engine-test.sh --fetch`, the suite in
  strict mode (which runs `scripts/check-surfaces.py` too), `glibc-test.sh` and `web-bench.sh --check`, and records the
  pass. `mise run r:github:publish` publishes only after a strict pass on the
  same sources and package (`ZEBKIT_RELEASE_UNCHECKED=1` publishes without and
  says so).
- `engine-test.sh` has `--fetch` (the downloads some tests need, apart from
  the run), `--strict` (`ENGINE_TEST_STRICT=1`: a skipped test or part of one
  fails, as a test that exits 0 after printing `FAIL` lines does) with
  `ENGINE_TEST_EXPECTED_SKIPS`, the skips it accepts, and `--only`, which
  fails when it matches no test. Each test has a profile of its own and the
  page server takes the port the system gives it; the tests share
  `tests/engine/harness.py`. On Windows it waits for the last test's engine
  children before removing its work directory.
- `release.sh --publish-only` publishes what was built without building; a
  version whose tag exists is never built or packed again (bump `VERSION`),
  an interrupted upload's draft is named, and a release missing an archive's
  `.sha256` is checked by GitHub's digest. `docker/publish.sh` lays out both
  SDKs with `scripts/zsdk-create.sh all`, builds, stops for the reports to be
  measured and committed, checks, and publishes. Heavy steps share one lock,
  `ZEBKIT_HEAVY_LOCK`.
- `scripts/bump-version.sh X.Y.Z` gives the checkout a new version, every
  manifest, lock file and README line that names it, and drops these notes'
  "draft" paragraph. Publishing (`mise run r:github:publish`, `release.sh
  --publish-only`) pushes `v<version>` and `bindings/golang/v<version>` at
  one commit before the release, through `gh`'s credentials where git
  cannot reach origin itself, and checks the Go module through the proxy.
  The release's order is written out in `docs/BUILD.md`, "Releases": bump,
  build, measure, commit, check, push, publish, then the crates and PyPI.
- `scripts/check-reports.py`, in `check.sh`: every report is of
  `upstream.lock`'s Chromium and Electron, and the size and benchmark reports
  say which engine they measured.
- `scripts/sandbox-helper-test.sh`, the Linux setuid helper installed from an
  archive and used, as root on a test machine; the suite runs its package side.
- `scripts/windows-toolchain.sh --verify`: MSVC and the Windows SDK are pinned
  by version and SHA-256 and checked from the disk before every release.
- One result format: a test passes only when its log ends with `N of N checks
  passed`. The C tests share `tests/engine/harness.h`. HTTP authentication,
  certificates and the user agent have one driver each, run in C, Python,
  JavaScript and Rust (the user agent also as a CDP client); the console's
  driver runs in Python, JavaScript and Rust, its C checks being in `hooks`;
  the popups' runs in Python and Rust, C's being `popup` (and `hooks`) and
  JavaScript's `window-open-javascript`. The hook groups run a group in one
  engine.
- New suite entries: `worker-websocket`, `automation-download-name`,
  `clipboard-permission`, `async-forms-javascript`, `native-host-input-<host>`,
  `offscreen-gpu-buffers`, `rust-engine`, `sandbox-helper` and the examples
  (`example-todo`, `example-gpui-browser`, `example-winit-host`; the suite
  compiles `examples/custom-titlebar` too).
